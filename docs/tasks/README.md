## 3. 任务书必填信息

| 字段 | 要求 |
| --- | --- |
| 身份 | 任务编号、修订、日期、负责人、当前状态 |
| 基线 | 完整代码 SHA、分支、工作区状态、远端核查时间；文档 SHA 与代码 SHA 分开 |
| 目标/问题 | 与章程、当前主线、问题编号及路线图阶段的关系；已有实现和待解决缺口 |
| 范围/非目标 | 明确允许路径与禁止变更；不能通过建议扩展已封版模块 |
| 前置与依赖 | 数据/来源身份、资源、平台、环境、授权与前序验收 |
| 操作许可 | 本地修改、提交推送、测试、只读生产、写生产、部署、高成本实验分别记录；未授权保持 NOT_AUTHORIZED |
| 设计 | 真实函数/调用链、复用方案、事务/读取/发布影响及备选方案 |
| 验收 Checklist | 可复核输入、预期输出、指标、规模、失败/取消/未知提交与安全用例；正式实验先登记协议 |
| 证据 | 命令、退出码、用例统计、覆盖率、CI run/job/attempt、精确 SHA、artifact 摘要及证据局限 |
| 回滚/交接 | 回滚条件、数据影响、剩余项、阻塞、下一步及需负责人裁决事项 |

性能任务额外记录整链边界、warmup、数据范围、股票数/Raw 行数、资源、开关、原始各轮
计时及排列、中位数/P95 定义、重叠阶段、输出等价和保留门槛。未执行即 NOT_RUN；
阈值不能在看到结果后调整，异常与失败样本保留，不能只报告局部提速。

## 4. 流程与审批

需求核对 → 基线/现状审阅 → 设计及必要负责人审阅 → 获批范围内实施 →
定向验证 → 对应范围完整验证 → diff/证据审阅 → 业务验收 → 经授权提交推送/运维。

提交与审阅顺序以负责人当前指令为准。若允许先推送触发普通 CI，任务仍停留在待验收状态，
不能因提交已存在而标 DONE。测试失败、资源不足或现场未授权须明确披露，不删断言/跳测刷绿。
业务代码、迁移、前端、部署的验证矩阵继续遵守 AGENTS。文档任务只做文档与 diff 检查，
不导入应用、读 .env、连接业务库或顺带执行测试/服务/迁移。
生产读取、写入、部署、恢复及高成本实验需要各自明确许可，普通 CI 和文档批准不能代替。

## 5. 状态定义

| 状态 | 含义与退出条件 |
| --- | --- |
| BACKLOG | 仅记录可能需求，未获优先级或执行许可 |
| PENDING_APPROVAL | 目标/范围/环境或前置审批未完成，不开展依赖该批准的动作 |
| READY | 范围、基线、设计、验收及必要授权明确，可以开始指定步骤 |
| IN_PROGRESS | 在批准范围实施/验证，必须有可接续进度与下一步 |
| REVIEW_PENDING | 已有具体文件/diff/证据待负责人审阅；未收到明确批准不能进入被限制步骤 |
| PARTIAL | 已交付部分实现，仍有验收缺口；列明已做/未做，不伪装为完成 |
| BLOCKED | 当前有明确前置阻塞；保留原因、解除条件和可独立工作的部分 |
| DEFERRED | 阶段延期，保留原因与重启条件；不是通过或被删除 |
| WITHDRAWN | 实现/实验候选被否决或撤回，保留提交与证据；原问题不自动关闭 |
| DONE | 本任务批准范围全部实现、必要验证和逐项验收完成，负责人确认；提交推送要求已按当前授权满足 |

UNKNOWN 表示未核实的事实；PENDING 表示结论/核查仍待完成；NOT_RUN 表示未执行。
这些不是成功状态，也不能用 skipped 代替。代码、工程 CI、业务正确性、性能/容量、
生产资格与任务完成状态分字段记录；例如“CI_SUCCESS + PERFORMANCE_OPEN”必须允许并存。

## 6. 结束、暂停与状态更新

每次任务交接（包括部分完成）在授权范围内同步 PROJECT_STATUS：

1. 核查时间、实际代码 SHA、工作区和远端事实；未提交修改与已发布提交分清。
2. 当前唯一执行任务、已完成步骤、未完成 Checklist、测试/CI 证据与适用版本。
3. 问题台账状态及关闭证据，不把撤回实现写成原问题已解决。
4. 阻塞、下一项具体操作、必要批准与禁止自动执行的步骤。
5. 阶段完成才更新路线图；主线/范围/门槛变化先追加 DECISION_LOG 并取得负责人批准。

治理文档提交推送只证明交付，不等于负责人最终验收或业务阶段完成。当前状态与本轮允许
修改的文件范围以 PROJECT_STATUS 和负责人最新要求为准；不得把最初的“五份新增文件”
当作以后每轮的变更范围。后续业务推进的四文档维护仍按 PROJECT_RULES 执行。
重复任务须链接原任务并说明差异，不另起一份互相矛盾的计划。会话聊天摘要不能替代仓库状态。

## 7. 换电脑 / 新会话接续

- 先核对已批准且已提交的最新治理基准；未提交草稿只在原电脑存在，不能声称已跨电脑同步。
- 工作区不干净时识别所属任务，保留用户改动，不自动清理、stash、reset、切分支或覆盖拉取。
- master 落后时先查差异与当前授权；不得为了接续自动覆盖本机状态或创建开发分支。
- 重查 GitHub 精确 SHA 的 CI；旧 run、旧覆盖率、缓存、历史签名不能授权当前源码。
- 检查状态中每个事实的证据时间和范围；数据库状态过期或未知就保持 UNKNOWN，不先连库猜测。
- 向负责人简要说明“基线、唯一任务、已经完成、尚缺、下一步”，然后仅继续已批准的步骤。
- 如果发现代码已超出状态文件，先做差异报告并修订事实；如 e610a92 的诊断部分实现与
  新的候选续项治理要求应同时记录，不能假装不存在或自行继续。
- 若无明确下一项批准，提交可审阅方案；不把长期目标自动转换成开发授权。
