# 补算跨网读取超时修复

## 范围

基线为未修改的 `4caa5ba`，本轮是工作区补丁。只修复计算 DataFrame 的大结果集传输及失败诊断，
不修改 Raw、策略公式、计算版本、PIT、Scheduler、候选协议或原子发布预算；不新增迁移。

## 根因与实测

- 原读取使用客户端缓冲的 `execute(...).mappings().all()`，整段结果必须在单条 SQL 超时前传完。
- 对所选 2025-02-01 至 2025-02-28，既有预热窗口实际从 2024-01-15 开始，不能缩短以规避问题。
- 云端只读复现原行情 SELECT，原 300 秒限制下在 300.703 秒返回 `57014/QueryCanceled`，
  驱动诊断明确为 `statement timeout`；观察到数据库等待 `ClientWrite`。
- 同范围使用修复后的服务端游标，在 REPEATABLE READ / READ ONLY 事务内完整读取 1,439,327 行，
  与同快照 COUNT 一致，耗时 541.828 秒；结束时 `statement_timeout=5min`、`transaction_read_only=on`。
- 本次没有提交或重跑任何云端补算任务，没有写入候选、替换已发布结果或修改既有失败历史。

## 实现

- 七类补算服务复用 `read_calculation_frame`，每次 FETCH 5000 行，批间沿用既有 checkpoint。
- 使用同一业务连接/事务/候选私有 VIEW，先收齐所有行再一次构造 DataFrame，保留顺序、全结果类型
  推断、空帧与横截面；并非每 5000 行计算一组，也不宣称总计算内存限定为 5000 行。
- 游标结束/失败/取消时关闭，不在 FETCH 中提交，不自动重试，不取消原 SQL 超时保护。
- 固定查询名、计数与耗时写入日志。错误摘要仅映射白名单原因和受限查询标签，不记录 SQL/参数/凭据。
- 补算预检仅记录日志，不在原质量门禁前新增提交；失败保留 `failed_stage` 和已达到的进度，
  不再统一退回初始 0%。

## 验证

- 最终 72 项定向回归通过，包括真实 PG17 缓冲读取超时/游标成功、类型/顺序/空值、取消、失败阶段
  保存、来源身份，以及实际补算/原子发布/质量拒绝。报告为忽略目录中的 `query-read-final-targeted.xml`。
- 完整 pytest 已运行：2141 项，2136 通过、5 失败，报告为 `query-read-final-full.xml`。
  其中预检进度写入新增提前提交，触发原事务门禁断言；已移除该提交，保留断言并通过最终定向回归。
  最终改动后另重跑全部单元测试：1542 通过、3 失败，事务门禁问题已通过；报告为 `query-read-final-unit.xml`。
  没有把修复前全量结果当作最新代码全绿，也未在最后诊断调整后再跑整套全集。
- 三项单元失败均为既有容量脚本顶层导入 Unix `resource` 导致 Windows 提前退出。
  未修改基线的对应两份单元文件复跑为 29 通过、相同 3 失败，见 `query-read-baseline-unit.xml`。
- Ruff、`git diff --check` 通过；未改动无关容量脚本、跳过用例或降低断言。
- 完整运行中的既有百万行 Retention 容量用例失败。另将未修改 `HEAD` 导出到忽略目录，以独立
  本机 PG17 合成库复跑，同一断言也失败：SQL 11，约 3096 ms，`RETENTION_RETRY_REQUIRED`，
  所有删除回滚。本轮全量中的同用例在 SQL 51、约 9548 ms 总耗时后保护性阻断；两者均为同一
  `RETENTION_RETRY_REQUIRED` 断言失败，不能混称相同执行计划。没有修改该模块、其 3 秒 SQL 预算或断言。
- 合成测试只使用显式指定的本机 PostgreSQL 17，不在云端业务库运行 pytest。

## 运行边界

本地 API 与 Worker 已在确认没有 RUNNING 任务后重启，前端保留，Scheduler 按用户要求保持停止。
服务器代码没有部署，旧失败任务没有自动重提。完整补算成功仍须用户显式提交后独立核验；
读取已验证不等于全部计算及发布已完成，跨网传输与后续计算仍可能耗时较长。
