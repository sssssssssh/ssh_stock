## 原因与已有失败

P3 `ef6e06d` / CI 39778639522 attempt 1 已完成 150 次同实例对照、60 份 EXPLAIN、
36 份实际 auto_explain。诊断根因为 CODE_SQL_PRIMARY：两个慢表的 B 缺失负探测
用同一个 PK 索引分别命中约 360 万/580 万块；C1 显式等值约 2000 块。
显式 ANALYZE 后仍复现，手动 EXPLAIN 也慢，不能把问题只归因 generic plan 或硬件。

P3 慢表 median 与完整代表负载门槛已达到，但快表 P95 失败：
C0/C1 为 0.088015/0.186568 秒。C1 异常样本 wall=0.215608 秒，
SQL execute=0.038045 秒、buffered row materialization=0.163842 秒、client CPU=0.181502 秒。
这是客户端阶段的成本，不得因 SQL 提速便忽略，也尚未证明一定由 GC 引起。
P3 失败完整保留在 [历史证据](evidence/v14_a422_p3_lookup_summary.json)，不作新 SHA 验收。

## 固定复核，不重试至通过

1. 不改变 public 5000×20、603040 行、B 503020 行快照、2000 个代表键、模型、索引、
   SQL、默认生产批量、统计阶段或资源设置。
2. 两个慢表仍每方案/统计状态五次；快表一次性固定为每方案/统计状态 100 次。
   C0/C1/C2/C3 全部同样轮换；首五次保留并参与完整三表工作负载，其余只增加快表尾部证据。
   所有原始样本保留，不去极值、不丢失败、不重置计数、不挑选最快结果。
3. 表 median/P95 使用该表全部固定重复；整体代表负载使用每轮三表实际 wall 求和后统计，
   不把各表 median 之和当整体。必须是同一实例内比较；跨 SHA 绝对时间不作收益计算。
4. 保持门槛：两个慢表 C1/C0 median≤0.70；整体 median≤0.80；快表 median≤1.10；
   所有代表表 C1/C0 P95≤1.10。资源与全部正确性不允许显著退化。
5. GC 只安装计时回调；不关闭、不强制收集、不改阈值。GC 是嵌套指标，不能与 JSON、
   行物化或总 wall 重复相加。容器内读取实际 backend PID 的 CPU/RSS，不能误读宿主同号 PID；
   VmHWM 标明进程生命周期峰值，不能冒充每查询独占峰值。
6. 保留 SQL 300 秒、全实验 100 分钟与 Job 120 分钟预算，不延长保护。
   若仍不满足，按不通过交付诊断，不再为获得 PASS 自动增加重复或更改标准。
7. 生产 SQL 在本轮复核之前保持 C0；只有全部条件通过，才使用用户授权的精确 C1 文件例外。
   原有其他生产文件、模型、迁移和历史证据继续冻结；不进入 A4-3/B/C。
