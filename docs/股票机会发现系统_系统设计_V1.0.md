# A股机会发现与趋势研究系统 - 系统设计文档

## L2 容量诊断包装

`data_publication_capacity_v12.py` 在已验证专用 PG17 的测试进程内包装原驱动依赖，
不修改 `run_level`、SQL、500 行批量、事务或发布实现。退出时恢复所有观测包装和事件监听器。
独立 `capacity-progress-v1` 只保存有界计数与阶段，表级边界原子写入，连续批次按时间节流。
逐行 payload 只累加内存计时；主线程 SQL 事件只计固定操作类型，不保存 SQL/参数。
表级 SQL 时间嵌套于 upsert/record_scope 等外层时间，不代表独占 CPU 或可直接相加的耗时。
进度与正式 schema/文件分离，正式 merge/release 门禁不变；异常仍形成 INCOMPLETE。
同名旧进度拒绝覆盖，不能复用旧 COMPLETE 收据；预期探针故障与真实失败区分。
设计证据和剩余 L2 细分项见 [诊断报告](acceptance/v14_a4_2_1_l2_diagnosis.md)。

## V1.4 A4-2.2 查找诊断

独立 `lookup-diagnosis` Job 在 CI 自建 PG17 上运行正式迁移与 5000×20 public 合成夹具。
冻结原 Python 查找体，仅在实验代理中替换候选关联条件；生产代码不引用诊断脚本。
C0 原 SQL、C1 显式等值、C2 集合关联、C3 100/500/1000；固定代表键、五轮交替，
原统计/ANALYZE 后分别采集 actual JSON plan、buffers、PG counters、CPU/RSS 与等待采样。
合成候选直接装载仅作查找诊断，不作真实 upsert/原子发布验收。
容量 Job 需同 SHA 候选匹配且性能证据就绪才调度；未就绪 Release Gate 仍失败关闭。
不调整模型/索引/公式/生产默认批量/读开关，不允许业务连接。
`dependency-audit` 独立 Job 输出带 SHA/run/attempt/lock SHA 的完整报告，失败输出另一种
INCOMPLETE 工件。聚合门禁复用 Node 的 schema/counts/lockfile 校验，不使用宽松替代解析。
容器就绪检查使用 TCP 排除初始化临时 socket 服务，随后双身份校验不变。

## V1.4 A4-2 实验架构

生产源码/迁移/配置与 A4-1 原证据冻结在 f8df915。实验只在双重身份验证的独立 PG17 UUID 子库运行，
复用原 Profile、真实 ServerCursor 和事务/发布回归。Q0 原始/服务/等保护包裹分别列出，
完整读入及最终复核计入同口径总成本；实验触发器/缓存不是生产可信凭据，不提供启用入口。
S3 物化/内联/窄键、S4 类型反关联和 S5 排序位置变体只存在于实验脚本，仍先执行完整 E0 校验。
窗口矩阵必须与完整单次读取比较；三个月复现保留 430 自然日输入和跨提交 root 读集。
E3 仅在验证后的 UUID 子库安装实验触发器，回滚/特权反例使其不能作为生产证书；
不新增业务迁移或索引。资源/真实游标/故障收据与限制见 [结果](acceptance/v14_a4_2_experiment_results.md)。
实验 JSON 在行数核对前保存已取得的表/索引元数据，失败记录阶段、错误类和 SQLSTATE，不输出 SQL 参数。
样本核对在同一快照以命名游标完整扫描 A/B 并记录 EOF/关闭/计数证据，不减行数或提高 SQL 预算。
连续月链每月读入仍执行原 E0 校验，末尾仅一次最终复核；链成本先逐轮合计实际跨度，再取中位数。

生产七份读链路源码必须逐字节等于审阅 SHA，否则诊断拒绝启动。
测试进程临时观测真实 psycopg ServerCursor、SQLAlchemy 事件及 DataFrame 构造/排序，
保留原调用、批量和异常并在 finally 恢复；不在业务入口增加 instrumentation。
记录 T1–T8、命名游标 DECLARE/FETCH、来源摘要、实际计划及资源原始计数；
普通 SELECT ANALYZE、游标估计及独立 untimed auto_explain 游标计划明确区分。
完整读入、最终来源复核、Golden 归一化各自计时，不能把嵌套时间/累计 RSS 当作独占成本。

trading_calendar_guard 要求请求范围逐日 TradeCalendar 完整，使用现有 is_open（包括半日 session）；
API 在入队前 422，Worker 在创建 PublicationWorkspace 前复核，直接/内部补算在预热前独立复核。
旧队列走既有 FAILED 状态，无新 DB 状态或迁移，不借用 Raw 行数推断日历。
冻结 Q0 / 实例身份门禁见 acceptance/v14_read_baseline.md。仅接管 factors.trade_status；
其他 TEMP VIEW、候选写前查询、base_row、质量/原子发布及计算公式保持原契约。
ab_merge_read 在合并后过滤身份，所有候选（含 tombstone）先验证 date/key 一致。
单次读使用事务 SHARE 锁稳定 A/B，当前根的公开读集逐日 SHA256 跨阶段及发布前核验，
不生成任何历史复用信任或来源凭据。AB_MERGE_READ_ENABLED 默认 false。
Q2 在同一锁定事务按可信开市日计数划分互不重叠的日历闭区间，保留休市日存量行，
每窗 yield_per=5000，统一构造/排序整帧后交原引擎；观测首行/5000/FETCH/整窗，不新增提交点。
来源校验与新范围捕获合并一次扫描，最终发布前仍独立核验；保护开销包含在对照总耗时中。
当前百万探索不满足性能目标，默认关闭不变；规模/物理布局/行宽/缓存限制见阶段 A 审阅。

## V1.3 测量基线

候选性能脚本在导入业务配置前验证显式 loopback 测试目标，唯一合成库经正式 Alembic 建模。
固定 9a377e4 实现与当前实现共用测量入口，区分候选准备、SQL 执行与根发布时间，
保存 SQL 数、操作分位数、EXPLAIN ANALYZE BUFFERS、RSS/WAL 和原像/候选摘要。
缓存未受控时明确记录，不宣称冷缓存或生产效果；现有事务、冻结身份和 0058 schema 暂不改变。
候选查询通过有界 JSON recordset 生成原生自然键，以完整 publication/table/row_key 闭区间点查
及完整主键排序锁定访问路径，避免空统计下扫描日期前缀；公开行在同事务内按自然键查回。
同批复用原像及事务时间；候选 INSERT 使用原生 composite recordset、固定 500 行及原冲突列白名单，
不绕过约束/审计触发器，也不覆盖首次 base_row。来源登记合并凭据失效并过期 Session 缓存。
每批 store 前保留原 checkpoint；取消 API 的 NO KEY UPDATE 兼容外键 KEY SHARE，
不改变 CAS、root FIFO、未知提交占槽、质量门禁或发布预算。scope 差集实现经测量后暂不重写。
测量分别记录 SQL 驱动耗时、SELECT 1 RTT、独立 RR 读者、I/O/WAL/TOAST/RSS；
不能将 SQL 语句数等同于线协议包数，也不能伪造纯网络等待时间。详见 [收尾证据](acceptance/v13_closeout.md)。

## 计算批次遥测

`services/calculation_progress.py` 使用执行上下文和线程安全、最多 12 个事件的内存快照记录阶段内操作。
固定标签与阶段白名单不接收 SQL、参数或原始异常文本。DataFrame 读取、计算器调用、范围核对、
候选 upsert 的每 500 行及最终发布逐表报告步骤；不增加输入 COUNT，不改 SQL/批大小或计算口径。
`job_worker` 将同一快照对象交给既有独立心跳线程，沿原间隔记录等待日志并在独立 Session 中合并
`job_metadata.calculation_progress`，仅更新匹配 RUNNING/worker/token 的任务。
明细写入使用 1 秒 lock_timeout、3 秒 statement_timeout，异常沿既有心跳错误路径脱敏记录；
不调用计算 Session.commit，不解锁/取消业务，不改 Published 表或候选账本。
推进时间用最近实际完成事件与数据库旧值的较大值，重复等待不推进；延迟的旧快照不能覆盖新明细。
阶段/终态更新一并保留最新明细，终态仍与既有候选发布协议一致。最终发布持有任务锁期间，
旁路写入可超时暂缓，逐表日志继续记录；不为展示进度提前提交该事务。
前端从既有 Job API 元数据读取明细，独立显示本步骤百分比、等待计时与有界记录，不解释为持久提交。
历史任务使用默认折叠的原生 details，明细占独立网格行，避免错误/明细与相邻任务重叠。
无 Schema、计算版本或部署自动切换；在途进程继续执行已加载旧代码，须在安全停机后再加载日志补丁。

## 计算 DataFrame 的有界传输

交易状态、因子、市场、行业、题材、趋势和机会查询通过 `repositories/calculation_frame.py` 保留原筛选/排序、
连接与事务，以 `yield_per=5000` 的 PostgreSQL named cursor/分批 FETCH 接收结果，结束或失败关闭游标。
每批后执行既有 checkpoint；不在游标中提交、不另开业务读取连接、不改变候选私有 VIEW 或快照。
保留全部行后一次构造 DataFrame，维持全结果 dtype 推断、空帧行为、排序及全市场计算输入；
这不是计算内存上限。DECLARE/FETCH 仍受既有 statement_timeout 约束，不提供无界 SQL 或自动重试。

固定查询标签、行数和 elapsed_seconds 写入脱敏日志；失败向原 SQLAlchemy 异常附查询标签，
数据库摘要仅追加白名单取消原因，保留原 SQLSTATE 和断连判定。补算失败保存 failed_stage，
预检明确标记 raw_prerequisites 且只记录日志，不新增预检前提交；不新增迁移、改写历史错误
或改变既有发布/身份/金融协议。

## 数据任务队列与安全取消专项（基线 7babdd2）

仍使用 PostgreSQL job_run；0057 增加可空 execution_started_at/cancel_requested_at/last_progress_at、
request_fingerprint、execution_token 以及 RESTRICT 的 parent_job_id/depends_on_job_id。旧行不回填推断。
部分唯一索引只保护 QUEUED/RUNNING 的非 NULL 指纹；FIFO/引用索引与保留清单同步。请求指纹覆盖规范化参数及
Analysis/Opportunity/算法和各计算版本，不包含来源文案或提交时间。依赖只能指向创建时已存在的顶层数据记录，
且无修改入口，从创建次序形成 DAG；数据库另拒绝自引用。

入队和领取共用 advisory transaction lock。DATA_MUTATION 允许多条等待；领取前检查顶层 RUNNING 与
Research RUNNING，锁定最早可运行数据行，不使用 SKIP LOCKED 越过数据队首。非数据通道沿用 SKIP LOCKED，
不纳入数据并发度。依赖未终态暂不领取；非 SUCCESS 的依赖终态让消费者 BLOCKED。数据优先策略可能使 Research
在持续数据队列下长期等待，这是明确的 P0 政策；已运行 Research 不因新 QUEUED 被退回队列。

领取生成 token、实际执行时间、worker_id，并将原凭据传给执行入口，不能在派发时冒领新的数据库 token。
数据进度/终态 CAS 检查 RUNNING、worker_id、token；SUCCESS/PARTIAL 额外检查 cancel_requested=false。
新格式派生行在来源 Job SUCCESS 前不计入分析就绪/覆盖计数；物理结果保留，不重解释旧来源或重写历史。
取消 API 与领取使用同一过程锁，并在行锁下重新读取；仅记录取消审计或将 QUEUED 立即置 CANCELLED，不覆盖阶段。
ContextVar 保存数据执行范围；独立短只读事务检查取消/所有权。阶段 update_job、质量日期循环、Provider 调用/重试
提供检查点；取消信号不被 best-effort Exception 路径吞掉。Worker 回滚当前事务，重开 Dirty（不增重试），
依次结束子任务与父任务后才释放槽位。Catch-up 内部补算同步执行、继承父 token 并有 execution_owner，不能再被领取。

任务专用 Session 每次新事务设置 SET LOCAL statement_timeout/lock_timeout（默认 300000/5000ms），
不会污染连接池其他业务。入队/取消/领取也有事务内有限等待。Tushare SDK timeout 使用实际支持的 pro_api 参数，
默认单次 30 秒、最多 3 次、退避最多 10 秒，重试之间查取消；调用及计算块内部不承诺抢占式中断。
last_progress_at 不由独立心跳更新；默认 600 秒无进度、120 秒取消等待只派生提示，不篡改状态。

数据 RUNNING 与运行中 Research 不再仅靠旧心跳转 FAILED，避免旧执行者继续写而新 Writer 已放行。
QUEUED 数据无隐式过期。异常中止保持安全阻塞，须人工确认旧执行者/写事务已停再对账，不自动续算。
本版没有逐行业务写 fencing 或受监督子进程，不允许主动接管仍可能运行的旧 token。
数据执行连接失效或待回滚首因未知时绕过普通 FAILED 路径，尽力以所有权 CAS 保存 execution_unconfirmed，
仍保持 RUNNING 和槽位阻塞；审计不可用时也不放行。已明确收到 PostgreSQL 语句终止响应的超时可回滚后失败。
新队列按冻结身份复核；旧排队缺完整快照明确 FAILED/JOB_CONFIG_SNAPSHOT_MISSING，旧结果照常读取。

GET /jobs/queue 返回完整顶层 running/queued 及位置、依赖状态；历史 GET /jobs 继续分页。
创建响应 meta.accepted/deduplicated 区分入队与去重，取消响应区分 accepted/completed。新字段为增量，不公开 token。
前端合并完整活跃队列与历史页，继承单飞与 60 秒统计节流；旧活跃任务离开历史页时仅刷新统计，不编造终态。

## 1. 系统边界

系统是一个**收盘后日线级投研系统**，不是实时交易系统。

输入：Tushare 历史/当日行情、股票基础、复权、每日指标、指数、行业分类与成分，可选资金流/涨停特色数据。  
处理：数据清洗 -> 复权 -> 因子 -> RPS -> 市场 -> 板块 -> 个股评分 -> 状态机 -> 信号 -> 后验统计。  
输出：REST API + Web Dashboard + 每日结构化复盘。

核心约束：

- 所有信号只能使用信号日及以前的数据；
- 策略结果必须可重放；
- 每个因子/评分必须能解释；
- 数据源与策略解耦；
- P1/P2 数据权限不足不能导致 P0 失败。

增强接口独立 capability：

### 6.2 Tushare 调用原则

- `daily(trade_date=...)` 按交易日一次拉全市场，而不是循环股票；
- `adj_factor(trade_date=...)` 同样按日拉；
- `daily_basic(trade_date=...)` 按日拉；
- 初次历史回填按交易日循环，`index_daily` 使用指数代码 + 日期区间批量拉取，并有进程级限速/重试；
- HTTP/SDK 错误使用指数退避；
- 每次请求记录 api_name、trade_date、elapsed_ms、row_count、status；Provider 日志使用独立 Session，不提交业务 Session；
- 达到 `config/strategy.yaml` 中 `provider.tushare.safe_limits` 时记录疑似截断 WARNING；
- token 不写日志。

## 8. 复权设计

### 8.1 原始数据

`stock_daily` 永远保存 Tushare `daily` 未复权 OHLC。

### 8.2 因子计算价格

使用：

```python
adj_close = close * adj_factor
adj_open  = open  * adj_factor
adj_high  = high  * adj_factor
adj_low   = low   * adj_factor
```

该序列用于计算收益、均线、突破等相对结构。页面若展示用户熟悉的前复权 K 线，可在查询层按区间最后一个复权因子归一化：

```python
qfq_close = close * adj_factor / latest_adj_factor_in_query_asof
```

**回测计算禁止使用查询区间未来日期的因子归一化逻辑产生未来信息。** 实际策略因子使用乘因子的稳定序列。

## 9. 因子计算实现

### 9.1 计算顺序

1. Load 最近 300~320 交易日的 OHLCV + adj_factor；
2. 生成 adjusted OHLC；
3. 按 ts_code 计算 rolling 因子；
4. 生成当日 Eligible Universe；
5. 在当日 eligible 截面计算 RPS；
6. upsert `stock_factor_daily`。

### 9.2 MA

```python
ma_n = adj_close.rolling(n, min_periods=n).mean()
```

### 9.3 收益

```python
return_n = adj_close / adj_close.shift(n) - 1
```

### 9.4 MA 斜率

V1 使用相对变化，便于跨价格比较：

```python
ma20_slope5 = (ma20 / ma20.shift(5) - 1) / 5
ma60_slope10 = (ma60 / ma60.shift(10) - 1) / 10
```

### 9.5 ATR20

True Range：

```text
TR = max(
    high-low,
    abs(high-prev_close),
    abs(low-prev_close)
)
ATR20 = mean(TR, 20)
ATR20Pct = ATR20 / adj_close
```

使用 adjusted OHLC 计算。

### 9.6 趋势效率

```python
net_move = abs(adj_close / adj_close.shift(20) - 1)
path = abs(adj_close.pct_change()).rolling(20).sum()
trend_efficiency20 = clip(net_move / path, 0, 1)
```

### 9.7 RPS

每日全市场横截面：

```python
rps_n = return_n.rank(pct=True, method="average") * 100
```

只在 `eligible=true` 股票中排名；不合格股票 RPS 可保留 null。

### 9.8 Drawdown

```python
rolling_high60 = adj_close.rolling(60).max()
drawdown_high60 = adj_close / rolling_high60 - 1
```

60 日最大回撤：对窗口内累计曲线计算 peak-to-trough，V1 可用 rolling max 后最小 drawdown 近似。

### 9.9 突破

必须排除当天：

```python
prev_high20 = adj_high.shift(1).rolling(20).max()
breakout20 = adj_close > prev_high20
```

### 9.10 Cross Above

```python
cross_above_ma60 = (
    adj_close > ma60
    and adj_close.shift(1) <= ma60.shift(1)
)
```

## 10. 评分实现

所有子分数统一 `0~100`。连续变量优先使用**截面 percentile**或线性 clip 映射，减少魔法值。

### 10.1 RightSideScore

建议实现为独立纯函数，并返回 `(score, components, reason_codes)`。

```text
RightSide =
  0.20 * BreakoutScore
+ 0.15 * MA20TurnScore
+ 0.15 * MARecoveryScore
+ 0.20 * RPSAccelerationScore
+ 0.10 * VolumeConfirmationScore
+ 0.10 * HigherLowScore
+ 0.10 * VolatilityStructureScore
```

#### BreakoutScore

- Breakout60: 100
- Breakout20: 85
- close >= 0.98*PrevHigh20: 60
- close >= 0.95*PrevHigh20: 30
- else 0

#### MA20TurnScore

根据 `ma20_slope5` 和 5 日前 slope：

- 由负转正：100
- 当前明显为正：80
- 走平且持续改善：50
- 仍明显下降：0

#### MARecoveryScore

- 今日 CrossAboveMA60：100
- close > MA60 且 5 日前 <= MA60：85
- close > MA20 且 MA20Slope5 > 0：60
- else 0

#### RPSAccelerationScore

组合：

- 当前 RPS20 截面值；
- `RPS20Delta5`；
- `RPS60Delta5`。

建议：`0.5*RPS20 + 0.3*percentile(RPS20Delta5) + 0.2*percentile(RPS60Delta5)`。

#### VolumeConfirmationScore

AmountRatio20 映射：

- >= 2.0 -> 100
- 1.5 -> 80
- 1.2 -> 60
- 1.0 -> 40
- <0.8 -> 10

用分段线性插值，避免硬跳。

#### HigherLowScore

- HigherLow 为真且低点提升 >= 5% -> 100
- 为真 -> 75
- 接近持平 -> 40
- 创新低 -> 0

#### VolatilityStructureScore

目标识别“筑底收敛 -> 突破扩张”。V1 简化：

- 前 20 日 ATR20Pct 低于过去 120 日的 40% 分位；
- 当日 TrueRange/ATR20 >= 1.0；
- 同时 Breakout20 时给高分。

数据不足时该项返回中性 50，而不是 0。

### 10.2 TrendScore

```text
TrendScore =
  0.15 * RPS20
+ 0.25 * RPS60
+ 0.15 * RPS120
+ 0.15 * MAStructureScore
+ 0.10 * SlopeScore
+ 0.10 * TrendEfficiencyScore
+ 0.10 * DrawdownQualityScore
```

#### MAStructureScore

四项各 25：

- close > MA20
- MA20 > MA60
- MA60 > MA120
- MA20Slope5 > 0 and MA60Slope10 >= 0

#### SlopeScore

将 ma20_slope5 / ma60_slope10 在当日 eligible 截面转 percentile，取 `0.6/0.4`。

#### TrendEfficiencyScore

`trend_efficiency20 * 100`，再可与 60 日版本组合（V1 先 20 日）。

#### DrawdownQualityScore

以 `drawdown_high60` 的截面分位反向打分；回撤越浅分越高。

## 11. 状态机实现细节

### 11.1 分类 API

```python
@dataclass
class StateDecision:
    state: str
    score: float
    reason_codes: list[str]
    fast_transition: bool = False


def decide_state(today, previous) -> StateDecision:
    ...
```

### 11.2 判定顺序

1. 先算 raw candidate conditions：is_s5/is_s4/is_s3/is_s0/is_s1；
2. 再读取 previous_state；
3. 应用 transition policy；
4. 写状态与 reason_codes。

### 11.3 转移矩阵

| From | Allowed To |
|---|---|
| S0 | S0,S1,S2,S3 |
| S1 | S0,S1,S2,S3 |
| S2 | S0,S1,S2,S3 |
| S3 | S2,S3,S4,S6 |
| S4 | S3,S4,S5,S6 |
| S5 | S4,S5,S6 |
| S6 | S0,S1,S2,S3,S4,S6 |

若 raw 条件从 S0 直接满足 S4/S5，落到 S3 且 `fast_transition=true`。

### 11.4 S3 有效期

S3 是事件型状态，不允许无限保留：

- 第一次确认 `state_day_count=1`；
- 最长 5 个交易日；
- 若趋势条件成熟 -> S4；
- 若确认失败 -> S2 或 S6。

## 12. Sector Engine 实现

### 12.1 行业收益

优先使用成分股**等权收益**作为自算行业收益，保证行业成分与个股因子口径一致：

```python
sector_return1 = mean(member_return1)
```

也可以存数据源板块指数收益用于对照，不能混为一个字段。

### 12.2 Point-in-time 注意

行业成员可能变更。V1 如果只获取最新成员，在长历史回测时会出现未来成分回看偏差。

系统要求：

- 数据库支持 `valid_from/valid_to`；
- Provider 能拿到历史有效期时立即使用；
- 如果暂时只能使用最新成分，回测输出必须 `membership_mode=LATEST_APPROX`；
- 真实策略日常运行不受该问题影响，因为使用当时最新成员。

### 12.3 Heat 截面打分

对每个 factor：

```python
percentile_score = factor.rank(pct=True) * 100
```

方向为“越小越好”的指标先取负数或 `100-rank`。

缺失可选因子时动态归一权重：

```python
active_weights = {k:v for k,v in weights if factor_available(k)}
normalized = v / sum(active_weights.values())
```

## 13. Market Engine 实现

### 13.1 指数趋势分

对配置的三类指数逐个计算：

- close > MA20
- MA20 > MA60
- Return20 > 0
- MA20Slope5 > 0

每项 25 分，得到 index score；三指数默认权重：沪深300 0.4、上证指数 0.2、中证1000 0.4。

### 13.2 Breadth

只用 eligible 股票：

```text
Breadth20 = count(close > MA20) / eligible_count
Breadth60 = count(close > MA60) / eligible_count
```

BreadthScore 默认：`0.6*Breadth20*100 + 0.4*Breadth60*100`。

### 13.3 AD Score

`up_rate = up_count / (up_count + down_count + flat_count)`，映射到 0~100，可直接 `up_rate*100`。

### 13.4 NewHighLow Score

```text
balance20 = new_high20 / max(new_high20 + new_low20, 1)
balance60 = new_high60 / max(new_high60 + new_low60, 1)
score = (0.6*balance20 + 0.4*balance60) * 100
```

### 13.5 Liquidity Score

`total_amount / MA20(total_amount)` 做滚动分位或 clip：0.7->20，1.0->50，1.3->80，1.6->100。

## 21. 回测与防未来函数

### 21.1 基本规则

- 信号日 t 的因子只能使用 `<= t`；
- Breakout rolling high 必须 `.shift(1)`；
- 行业成员尽量 point-in-time；
- 信号收益从下一交易日开始计算；
- `signal_forward_eval` 不允许进入特征查询；
- backtest service 与 factor service 分 package。

### 21.2 研究口径

V1 不直接模拟完整账户。优先做**事件研究**：

```text

 -> +5d return
 -> +10d return
 -> +20d return
 -> +60d return
 -> MFE/MAE
```

先验证“信号本身有没有信息量”，再开发组合回测。

### 21.3 V1.1 组合回测预留

接口：

```python
class BacktestStrategy(Protocol):
    def select(self, trade_date): ...
    def rebalance(self, trade_date): ...
    def exit(self, position, trade_date): ...
```

可后续接 RQAlpha/Backtrader，但 V1 不作为依赖。

## 34. 实现风险清单

1. **行业历史成分回看偏差**：必须标记 membership mode；
2. **复权因子更新**：重新计算相关日期或保证算法版本可重算；
3. **停牌导致时间序列缺口**：rolling 按股票实际交易记录处理，同时交易日 forward return 需按市场交易日对齐；
4. **ST 名称变化**：仅使用当前 stock_basic 名称会影响历史回测，V1 属近似，后续引入历史 ST 状态；
5. **新股幸存偏差**：使用 list_date 约束并保留退市股票做严谨回测；
6. **Tushare 高积分权限**：所有特色数据能力可关闭；
7. **算法过拟合**：V1 阈值是研究起点，不是交易真理；必须通过历史 out-of-sample 迭代；
8. **未来函数**：rolling high 必须 shift，行业成分和后验收益必须隔离。

---

**最终工程原则**：先构建可靠、可重复的数据与因子底座，再迭代策略。V1 的价值不是“预测上涨”，而是持续、稳定、可解释地把全市场压缩成少量值得研究的趋势候选。

### 36.10 自动运行与可靠性优化（2026-09-04）

本轮在不重构 Raw 数据层的前提下增强 Scheduler、DailyJob 和任务入口可靠性。

新增模块：

- `app.services.job_guard`：统一判断 `daily/sync_basic/backfill/recalculate/validate_data/catchup` 是否存在 `QUEUED/RUNNING` 活跃任务，并在检查前恢复 stale job。
- `app.jobs.catchup_job`：Scheduler 触发时使用的自动补漏编排器。它同步近期交易日历，分别判断 Raw 完整性和分析完整性，生成 `raw_required_dates`、`analysis_required_dates`、`refresh_dates` 三类计划。

服务行为：

- `DailyJob` 在四类 Raw 数据同步后执行 `check_raw_completeness(..., persist=True)`。`overall_status=ERROR` 时抛出 `DataQualityError`，不进入 `FactorService`、`MarketService`、`SectorService` 和 `TrendService`；`WARNING` 当前允许继续。
- RawCompleteness Gate 和跨表质量 Gate 在抛出错误前显式提交 `data_quality_daily`，保证 FAILED 任务仍保留 ERROR 证据。
- `job_run.job_metadata` 会记录 Raw Gate 的 `stock_daily_status`、`adj_factor_status`、`daily_basic_status`、`index_daily_status`、`current_day_datasets`、`current_day_status` 和 `current_day_invalid_counts`。
- Catch-up 的分析完整性由 `analysis_complete_dates()` / `is_analysis_complete()` 判断，必须满足当前 `config_hash`、`factor_v1/market_v1/sector_v1`、当前 `algo_version`，并且 `factor_vs_daily`、`state_vs_factor` 达到现有跨表质量 PASS 阈值；不得只用 `MAX(stock_state_daily.trade_date)` 或单表存在行作为完整依据。
- Catch-up 对 Raw 缺口先执行四类 Raw-only 同步和 RawCompleteness；全部通过后，将 Raw 与 Analysis 缺口合并，从最早缺口到最新 Raw 交易日创建一个 `recalculate` 任务并复用 `app.services.recalculation.run_recalculation()`。只有 Analysis 缺口时不访问 Tushare。
- 最近交易日 refresh 改为 Raw-only，直接调用 `IngestionService.sync_daily()`、`sync_adj_factor()`、`sync_daily_basic()`、`sync_index_daily()`；每个交易日 refresh 后执行 RawCompleteness 并提交质量结果，ERROR 失败，WARNING 继续。
- Raw-only refresh 之后如果存在可修复 dirty range，Scheduler 自动执行 Dirty Repair，从最早 dirty start 到最新 Raw 交易日；成功 `RESOLVED`，失败 `FAILED`。可修复范围为 `OPEN` 或 `FAILED` 且 `retry_count < dirty_max_retry_count`。
- API enqueue 入口保留 HTTP 409 语义，但内部改为调用统一 Guard。
- CLI 的 `daily`、`sync-basic`、`backfill`、`validate-data` 在执行前调用统一 Guard，避免与 API/Scheduler 长任务冲突。
- Scheduler 每次执行前调用 stale recovery。超时的 `QUEUED/RUNNING` 任务会设置为 `FAILED`，`finished_at=now`，`error_message=stale job recovered after process restart`。
- Scheduler 使用 `datetime.now(ZoneInfo(settings.app_timezone)).date()` 取业务日期，并将 crontab 风格的 `1-5` 映射为 APScheduler 的 `mon-fri`。
- Catch-up 缺口超过 `max_catchup_trade_days` 时只记录 warning 并跳过，避免空库或长期停机后自动拉多年历史。
- `BackfillJob` 的 `sync_index_daily_range()` 失败会 rollback 当前异常事务、写入 warning metadata，然后进入逐日 `sync_index_daily()` 兜底。

配置：

```yaml
app:
  scheduler:
    daily_cron: "10 18 * * 1-5"
    max_catchup_trade_days: 20
    queued_stale_hours: 24
    running_heartbeat_timeout_minutes: 15
    dirty_processing_timeout_minutes: 30
    stale_recovery_interval_seconds: 60
    refresh_recent_trade_days: 5
    dirty_max_retry_count: 3
```

本轮未新增表和迁移；Raw 数据层和自动运行层仍按 Milestone 8 范围封版。

## Milestone 13.3 Rebalance and Accounting design (2026-09-30)

`RebalancePlanner` and `AccountingEngine` are pure services. Batch market-data providers adapt StockDaily, StockBasic, current-identity Trade Status, and StockAdjFactor into domain DTOs. Application services own transactions, acquire the shared run-row lock, enforce `BACKTEST/RUNNING`, and persist plans, orders, positions, and NAV through `PortfolioRepository`.

Accounting replaces the same run/date position slice and upserts NAV, while planning is unique by run/signal date. This makes retries deterministic without a mutable current-account table.

The engine sequence is START_OF_DAY -> OPEN -> CLOSE -> AFTER_CLOSE. Corporate-action and inactive-holding gates run before OPEN; M13.2 executes persisted pending orders; accounting replays fills and values the close; rebalance then creates next-open children. The Backtest engine remains dependency-injected and ORM-free; public lifecycle orchestration is deferred.

### M16.1.1 Agent Reliability Closeout（2026-10-10）

执行服务使用可注入单调时钟记录从 Registry lookup、Pydantic 校验、同步 handler 到最终序列化的总耗时。`ToolSpec.timeout_seconds` 是返回后判定的软预算，不创建后台线程，也不声称能中止已发生的 CPU/数据库工作；PostgreSQL 单条语句继续由事务级 `statement_timeout` 硬取消。SQLSTATE `57014` 映射为安全的 `STATEMENT_TIMEOUT`，软预算映射为 `TOOL_TIMEOUT`，日志只记录白名单审计字段与错误码。

`ToolSpec.max_records` 只约束顶层 `records`；Spec 另行声明 Evidence、Warnings 与命名嵌套列表上限。`data.coverage` 先用有界 distinct dataset 查询执行 32 数据集 fail-closed gate，再构建完整聚合，不做静默截断。最终 DTO 仍在写入 HTTP envelope 前执行 64 KiB canonical JSON 字节检查；结构资源超限使用 `RESOURCE_LIMIT_EXCEEDED`，字节超限使用 `OUTPUT_LIMIT_EXCEEDED`。

Evidence v2 对规范化源身份、真实 `calc_run_id`（存在时）、质量限制和完整返回事实的 `content_hash` 再生成 `evidence_id`；请求 ID、当前时间不进入哈希。字典键和 Decimal 规范化保证确定性，覆盖率证据哈希包含完整日期区间逐数据集统计而非最后一天。旧字段保持兼容，无需回写历史数据。

M14 Agent 读取先完成无歧义 Performance 选择，再调用 `validate_exact_analytics_bundle()` 对已经选中的 Run/Performance/Risk/Trade/Period 做公共只读 owner、状态、日期和来源身份校验，绝不调用 Resolver 的 latest 选择或任何计算服务。Period 沿用 M14 概览契约为可选；缺失产生明确 warning，存在则必须属于同一 Bundle 且身份哈希一致。

Registry 构造器不再检查长度恰好为 8，而是校验名称唯一且合法、版本格式、允许 layer、`read_only=true`、handler/input model 与全部正向预算。默认 `build_registry()` 仍与八工具 allowlist 精确相等，API 的 `/status` 和 `/tools` 均从实际 Registry 计算 `tool_count`。

## Milestone 16.2.1：Reliability & Evidence Integrity Architecture

`AgentChatApplication` 在进入一轮处理时记录单调时钟绝对 Deadline，并在上下文读取、Provider、编排、
Evidence 编译和终态持久化前后检查。`ToolOrchestrator` 每次执行前计算 `remaining_seconds`，传给
`AgentApplicationService` 和 `agent_db_session`。有效工具软预算为剩余时间与 ToolSpec 预算的最小值；
事务级 PostgreSQL `statement_timeout` 再与配置值取最小并向下取至少 1 ms。同步 Python handler 无法
抢占式中止，返回后若越界即拒绝结果；SQLSTATE 57014 由数据库硬取消并映射为 `STATEMENT_TIMEOUT`。

最终 Provider 契约兼容增加结构化 `claims`。FACT/COMPARISON 包含受控 `records.<index>...` 路径、
值、单位、交易日、实体与 Evidence ID；EvidenceCompiler 只允许八工具的显式路径映射，并在同一实际
Tool Result 内完成实体、日期、单位及 Decimal 值匹配。百分比只支持确定性 decimal-to-percent 转换。
验证通过后由服务端从 Structured Facts 重建 Claim 文本和 marker；任何未验证模型文本不会进入正式
定量答案。INFERENCE 必须绑定证据并降为 WARNING；旧式无 Claims 草稿 fail closed。

`EvidenceComparisonPolicy` 在服务端处理 SAME_DATE_RANKING、ENTITY_OVER_TIME、
INDEPENDENT_BACKTESTS 与 TRAIN_VS_OOS。同日横向要求日期和计算身份一致；跨日同实体可比较但增加
上下文警告；独立回测要求 run/config/calc/source 身份；Train/OOS 必须按样本角色分离。策略输出
`COMPARISON_INCOMPATIBLE` 或 `COMPARISON_REQUIRES_CONTEXT:*`，Prompt 仅负责引导，不能覆盖判定。

新请求身份由 canonical JSON 中的 normalized content、chat ID、owner ID 和 contract version 生成无盐
SHA-256。内容先执行 Unicode NFKC、CRLF/CR 到 LF、逐行移除行尾空白，再稳定序列化。锁内查询
`(session_id, request_id)`：同 hash + COMPLETED 才重放；不同 hash 或历史 NULL hash 返回 409；
RUNNING/FAILED 保持受控冲突。迁移 `0048_m16_2_1_request_hash` 新增可空字段和格式约束，不回填历史；
`0049_m16_2_1_hash_name` 仅向前修正预发布环境中的重复约束前缀，不改数据，downgrade 为 no-op。

### M16.5.1 冻结 Claim 与 Report 创建一致性

Report v3 读取和创建共用 `verify_report`/`verify_archive_contract`。FACT 与 COMPARISON 按原序逐项核对 `evidence_id:path`，拒绝重复或错位；结构化 INFERENCE 不把继承引用当作自身直接字段，而是核对唯一且已验证的 FACT/COMPARISON 支持图、Evidence 子集和稳定去重的继承引用。旧 v1/v2 不应用 v3 支持图规则，现有 v3 JSON/Hash 不重写。

创建报告在 Archive 冻结复核后构建快照；Report 行 `flush` 后、`commit` 前调用与 GET/EXPORT 相同的完整校验和归档绑定核对。失败回滚，成功后返回预先验证的视图；同 request ID 继续按原请求哈希幂等回放。离线响应分别保留直接 `facts_status`、Claim `status`，并增加 `check_kind`、`facts_applicable`、推断 `support_status` 与结论汇总。比较缺 M14/M15 冻结合约时只能复核字段，不重新授予差值、排名或算法复现。
